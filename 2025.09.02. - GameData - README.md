    - 9.1 ActorComponent
        - 액터 컴포넌트
        특정 액터에 원하는 기능을 부여하기 위한 컴포넌트.
        지금까지의 컴포넌트들은 기능이 정해져 있고 누군가가 만들어둔걸 가져다 썼음.
        
        - StatusComponent
        우리가 제작할 액터 컴포넌트. 이벤트(피격, 스킬 사용, …)에 의해 액터의 스탯이 변경되면
        델리게이트에 바인드된 함수를 통해 액터의 스탯 변경을 알림.
        ex) 스탯컴포넌트와 UI 컴포넌트 사이의 느슨한 결합.

            ```cpp
            // SXStatusComponent.cpp
            
            #include "Component/SXStatusComponent.h"
            
            USXStatusComponent::USXStatusComponent()
            	: MaxHP(100.f)
            	, CurrentHP(100.f)
            	, bIsDead(false)
            {
            	PrimaryComponentTick.bCanEverTick = false;
            }
            
            float USXStatusComponent::ApplyDamage(float InDamage)
            {
            	const float PreviousHP = CurrentHP;
            	const float ActualDamage = FMath::Clamp<float>(InDamage, 0, PreviousHP);
            
            	SetCurrentHP(PreviousHP - ActualDamage);
            
            	return ActualDamage;
            }
            
            void USXStatusComponent::SetMaxHP(float InMaxHP)
            {
            	MaxHP = InMaxHP;
            
            	if (MaxHP < KINDA_SMALL_NUMBER)
            	{
            		MaxHP = 0.1f;
            	}
            
            	OnMaxHPChanged.Broadcast(MaxHP);
            }
            
            void USXStatusComponent::SetCurrentHP(float InCurrentHP)
            {
            	CurrentHP = InCurrentHP;
            	if (CurrentHP <= KINDA_SMALL_NUMBER)
            	{
            		CurrentHP = 0.f;
            		OnOutOfCurrentHP.Broadcast();
            
            		bIsDead = true;
            	}
            	OnCurrentHPChanged.Broadcast(CurrentHP);
            }
            
            ```
            
        
        - Transient 키워드
        개체의 어떤 속성들은 지금 현재 값이 개체마다 다른 경우가 있음.
        대표적으로 CurrentHP, CurrentMP 같은 속성들.
        이런 속성들은 개체의 시리얼라이즈에 포함될 필요가 없음. 이때 Transient 키워드를 사용함.
        ex. 레벨에 배치된 개체를 복사해서 붙혀넣기(시리얼라이즈와 디시리얼라이즈)할 때 
          원본 개체와 복사 개체는 굳이 CurrentHP와 CurrentMP가 같을 필요 없다.
        
        - bWantsInitializeComponent 속성
        액터의 PostInitializeComponents() 함수에 대응하는 컴포넌트 함수는 InitializeComponent()
        이 함수는 액터의 PostInitializeComponents() 함수가 호출되기 바로 전에 호출됨.
        이 함수를 사용해서 컴포넌트의 초기화 로직을 구현해주는데, 
        이 함수가 호출되려면 bWantsInitializeComponent 속성이 true여야 함.

        이번 절에서 구현할 HP UI는 캐릭터의 MaxHP 값과 CurrentHP 값을 알아야함.
        HP Widget을 보여주는 “기능”에 해당하므로 컴포넌트 방식으로 구현.

        액터의 BeginPlay() 이후에 위젯 컴포넌트의 InitWidget()이 호출됨.
        InitWidget() 이후에 자신을 소유한 액터를 알 수 있음.
        이 때문에 UI의 CDO에서 미리 초기화 할 수 없음. 복잡해지는 이유.
        관계도: 액터 - 위젯컴포넌트 - UI

        - 데이터를 관리할 클래스
        게임에 사용될 데이터가 여러 개체에 저장된다면?
        각 개체 속성 간의 동기화 문제가 생김. A 개체에선 10, B 개체에선 7, …

    - 9.6 Unreal C++ Module
        - 블루프린트 프로젝트 Vs. C++ 프로젝트
        프로젝트를 처음 만들 때 블루프린트와 C++을 골랐었음.
        C++ 코드를 작성하지 않는 프로젝트를 블루프린트 프로젝트라 함.
        C++ 프로젝트는 개발자가 직접 모듈을 추가하고 임포트 할 수 있음.
            
            
        - 언리얼 C++ 모듈
        언리얼 엔진의 소스코드는 모두 모듈 단위로 관리되고 있음.
        모듈 단위로 작성된 C++ 소스코드를 컴파일한 결과물은
        에디터용으로 .dll 파일, 실행 파일용으로 .lib가 생성됨. ex) UnrealEditor-{모듈명}.dll
        아주 간단하게 말하면 “소스파일의 빌드 결과물”을 모듈이라 할 수 있음.
        
        - 기존에 만들어진 언리얼 C++ 모듈 추가 방법
        1. 프로젝트 폴더 > Binaries > Win64 폴더에 해당 .dll 파일 추가.
        2. .uproject 파일 > Modules에 원하는 모듈이름 작성.
        위 두 가지 절차를 기억하고 새로 언리얼 C++ 모듈을 추가해보자.
        우리가 만든 소스코드가 빌드된 .dll 파일이 Win64 폴더에 추가되어야 하고,
        .uproject 파일의 Modules에 우리가 만든 모듈의 이름을 작성하면 되는 것.
        
        - 언리얼 C++ 모듈 소스코드 관리
        언리얼 C++ 모듈 소스코드도 결국 프로젝트 폴더 > Source 폴더에 저장되어야 함.
        그럼 UBT이 Source 폴더의 소스코드를 바탕으로 플랫폼(Win, Mac, …)에 맞춰서 빌드.
        C# 언어에 내장된 Compile on-the-fly 기능을 활용해서 런타임 중에 .cs 파일을 읽고
        빌드 환경을 구축하여 해당 모듈을 포함하여 빌드 진행.
        
        - Source 폴더 구조
        **타겟 설정 파일들**
        해당 프로젝트가 사용하게 될, 즉 빌드 대상을 지정함.

        {프로젝트명}Editor.Target.cs: 에디터 빌드 설정 파일

        - PublicDependencyModuleNames Vs. PrivateDependencyModuleNames
        만약 A 모듈의 클래스들을 우리 모듈의 .h 파일과 .cpp 파일 모두에서 사용한다면 Public.
        우리 모듈의 .h 파일과 .cpp 파일 모두에서 사용되면, 또 다른 B 모듈이 우리 모듈을 
        참조할 때도 문제 되지 않게끔 하기 위해서 Public Dependency에 A 모듈을 넣어야만 함.
        근데 만약 A 모듈의 클래스들을 우리 모듈의 .cpp 파일에서만 사용한다면 
        A 모듈을 Private Dependency에 넣음. B 모듈은 A 모듈의 존재를 몰라도 되기 때문.
        
        - 매크로를 통한 모듈 정의
        IMPLEMENT_MODULE(): 일반 모듈
        IMPLEMENT_GAME_MODULE(): 게임 모듈
        IMPLEMENT_PRIMARY_GAME_MODULE(): 주 게임 모듈
        일반적으로 하나의 게임 프로젝트에는 하나의 주 게임 모듈 매크로가 선언되어야 함.

        - 비동기 애셋 로딩
        FStreamableManager라는 구조체가 제공됨. 
        이 매니저 구조체는 프로젝트에서 하나만 활성하는 것이 바람직하기 때문에
        GameInstance 클래스에서 관리하는 것이 권장됨. 
        FStreamableManager에서 비동기 방식으로 애셋을 로딩하는 함수는 AsyncLoad() 함수.
        해당 함수에 FStreamableDelegate 형식의 델리게이트를 넘겨줄 경우,
        애셋 로딩이 완료될 때 해당 델리게이트에 연결된 함수를 호출해줌.
        FStreamableDelegate 형식으로 델리게이트 속성을 선언하고 넘겨줄 수 있지만,
        델리게이트에서 제공하는 CreateLambda() 함수를 사용해서 델리게이트를 새로 생성해서
        넘겨주는 방식도 괜찮음.
        
        - 애셋 로딩 방법을 결정하는 기준.
        생성자에서 미리 로딩: 프로젝트 전반적으로 해당 애셋이 필수인 경우.
        런타임에서 동기적으로 로딩: 사용 안할수도 있지만, 사용전 반드시 로드되야 하는 경우.
        런타임에서 비동기적으로 로딩: 꼭 사용전에 로드될 필요는 없는 경우.
